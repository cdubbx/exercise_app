What this integration does

The Exercise Bot is a chat feature for general workout planning and exercise questions. The phone app sends a question to the Exercise Plus server. The server checks the request, sends it to OpenAI’s Responses API, and returns the answer to the app. When you clearly ask to schedule a workout, the bot can prepare a calendar proposal using exercises from the app’s library.

The bot cannot write directly to the calendar. The app shows the proposed day, time, exercises, sets, and reps; you review it and tap Add to calendar. The normal workout API then saves the plan under your account.

How a chat request moves through the app

  1. You must be signed in, and the app requires your AI-sharing consent before sending a question.
  2. The app sends POST /api/gpt-chat/ with your current query and recent conversation messages. Each history item has a role (user or assistant) and text content. The app includes up to 12 recent messages.
  3. Django checks that the question is present and no longer than 2,000 characters. It checks the conversation format and limits each history message to 2,000 characters. It then applies a limit of 20 chat requests per user per minute.
  4. The server adds its fixed coaching instructions. They ask for practical, concise advice; safe, beginner-aware training suggestions; no diagnosis or treatment; and phone-friendly Markdown without tables or HTML.
  5. The server sends the message, recent history, instructions, and a calendar-proposal tool definition to OpenAI. The API key stays in the server configuration. The phone never receives it.
  6. The server reads the generated reply. If OpenAI proposes a calendar action, Django checks the requested day, time, exercise count, and each exercise against the app’s library before returning a proposal.
  7. The app displays the reply and, when available, a reviewable workout card. You choose whether to add it. The app submits the accepted plan through the planned-workout API.

What the app sends

The request uses the signed-in user’s normal Exercise Plus access token. The bot does not need your Spotify or AWS credentials. The server adds previous chat turns only to give OpenAI enough context to answer follow-up questions.

POST /api/gpt-chat/
Authorization: Bearer <Exercise Plus access token>
Content-Type: application/json

{
  "query": "Plan a back workout for Monday evening",
  "conversation": [
    {"role": "user", "content": "I prefer dumbbells"},
    {"role": "assistant", "content": "I can suggest a dumbbell plan."}
  ]
}

The server accepts only user and assistant history roles. It passes no more than the latest 12 history items to OpenAI. The current question and each history message must be between 1 and 2,000 characters. If the app is not signed in, the request is rejected.

How workout proposals are checked

The server gives OpenAI a structured function called propose_calendar_workout. This is a request to prepare data in a known shape; it is not permission to write to your account. The proposal has one weekday, one time slot, and between 1 and 8 exercises. Each exercise needs a library name, a set count from 1 to 100, and a repetition count from 1 to 1,000. Time slots are Morning, Afternoon, Evening, or Anytime; Anytime is used when you did not specify a time.

Django looks up every proposed exercise in the library, including a small set of common alternate names such as “pull-ups” for “Pullups.” If even one exercise cannot be matched, the server returns no calendar action and tells the bot to ask for a library exercise name. It does not quietly save a partial plan.

A valid reply contains gpt_response, an empty exercises list retained for the current app response format, and calendar_action set to the checked plan (or null when there is no usable proposal). The app’s Add button is the point where the user confirms. Saving then goes through the planned-workout endpoint, which checks the workout again and stores it in the selected weekday/time slot.

{
  "gpt_response": "I prepared this evening workout for Monday. Review it, then tap Add to calendar.",
  "exercises": [],
  "calendar_action": {
    "day": "Monday",
    "time_of_day": "Evening",
    "workouts": [
      {"exercise": {"id": "…", "name": "Bent Over Barbell Row"}, "sets": 3, "reps": 10}
    ]
  }
}

A chat reply by itself is only coaching text. It does not mean anything has been placed on the calendar.

Prompt caching and chat storage

The server sends the same coaching instructions and tool rules before the changing conversation. OpenAI prompt caching can reuse an identical starting portion of a request when the model and cache rules allow it. Reuse can reduce the cost of repeated input and may reduce processing time; it does not reuse the answer, so each reply is generated anew. The cache needs a sufficiently long, matching prompt prefix. The minimum length depends on the selected model, so a cache hit is not guaranteed.

Exercise Plus sends a stable prompt_cache_key derived from a one-way hash of the account’s internal ID. The same account therefore uses a consistent cache group; the raw account ID is not sent as the key. This key helps group or route requests for caching. It is not chat history, a sign-in token, or a separate privacy boundary.

The server sets store: false on Responses API requests. This tells the Responses API not to retain the response as a stored response object. It does not, by itself, mean OpenAI has zero data retention for the account: other provider data controls and abuse-monitoring rules are separate. Prompt caching can also temporarily hold encrypted cached input data under OpenAI’s cache rules. The app sends the conversation history it has for the chat on each request, while the Exercise Plus chat endpoint does not write these messages into its own chat-history database. Review the current OpenAI API data controls and prompt caching documentation for provider-side handling.

The backend logs the total input-token count and any cached-input-token count returned by OpenAI. It does not log the question or answer in that usage message.

Configuration and limits

SettingPurposeRequired?
OPENAI_API_KEYSecret key the server uses to call OpenAI. Keep it in protected server configuration; never put it in the mobile app or source control.Yes
OPENAI_MODELSelects the model used for replies. If unset, the backend uses gpt-4.1-mini.No

The backend allows 20 chat requests per signed-in user per minute. A limit response is HTTP 429; wait and try again. If the API key is missing or OpenAI has no available API credits, the app receives a service-unavailable response. Temporary network or provider failures also return a retryable service error. The server does not expose the provider’s secret error details to the app.

OpenAI API billing is separate from a ChatGPT subscription. The API account needs an active payment method or available credits for requests to succeed.
