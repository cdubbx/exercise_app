Image uploads with S3

S3 is Amazon’s file-storage service. This integration uses it to keep profile and exercise images outside the database, in a private storage area called a bucket. The app sends images to our server first; the server checks and cleans them before saving them to S3. The server, not the phone app, has the AWS access needed to write the files.

What happens when you upload an image

  1. You choose one photo in the app. The app checks the file size and prepares it for upload. The server checks it again because a phone-side check alone cannot protect the service.
  2. The signed-in app sends POST /api/uploads/ with two pieces: path set to profile or exercises, and file containing the image. This upload format is called multipart/form-data; it lets a request carry both small text fields and the actual file.
  3. The server accepts JPEG, PNG, or WebP files up to 5 MB and 16 megapixels (16 million image dots). It checks that the file is a real image, fixes its orientation, shrinks it to fit within 2048 by 2048 pixels, and saves a fresh copy. Re-saving the pixels removes hidden photo details such as location and camera information. The cleaned image must still be no larger than 5 MB.
  4. The server gives the file a new, random name and stores it under the selected folder and your account ID, for example profile-images/<your-user-id>/<random-id>.jpg. That storage address is an S3 object key: the file’s name and folder path inside the bucket. The server does not mark the file public.
  5. The server replies with a temporary signed link so the app can show the upload. The upload endpoint is limited to 20 requests per account per hour.

How the app saves and displays the image later

When the app attaches the uploaded image to a profile or custom workout, it sends the temporary link back with that record. The server checks that the link belongs to this bucket and to the signed-in account’s folder. It removes the temporary signature and saves only the stable bucket address with the record. This avoids saving a link that will stop working after an hour.

When the app later loads a profile or workout, the server creates a fresh pre-signed link for the private image. This link is like a short-term pass: anyone who has it can view that image until the link expires. Links expire after one hour. The app can get a fresh link the next time it loads the record. Avoid sharing these links or putting them in logs.

In local development, if no S3 bucket is configured and Django is in debug mode, images are saved in the local media folder instead. On the live server, missing S3 configuration produces a clear storage error; the app does not silently save files to Heroku’s temporary disk.

Current limitation: deleting an Exercise Plus account deletes its database records, but the current delete-account method does not remove that user’s image files from S3. Those files can remain in the bucket. The AWS permissions below reflect the upload and display features that are implemented today; file cleanup needs to be added before account deletion can remove S3 images automatically.

Code: ImageUploadView.post receives and stores the image; canonical_media checks and saves its stable address; display_media creates its temporary display link.

AWS S3 setup and access

Create or select the intended private bucket and region, then set AWS_STORAGE_BUCKET_NAME and AWS_S3_REGION_NAME on the server. boto3 is the AWS toolkit this Python server uses; it reads AWS credentials from the server environment. On Heroku, use a dedicated IAM user (an AWS identity made for this app) and store its credentials in protected Heroku settings. Where your hosting platform supports it, an attached IAM role (permissions assigned directly to the running server) is safer because you do not need to store a long-lived secret. Never use an administrator identity or put AWS credentials in the phone app.

The app stores images under these account-specific paths:

profile-images/<user-id>/<random-id>.(jpg|png|webp)
exercises-images/<user-id>/<random-id>.(jpg|png|webp)
S3 actionPurpose
s3:PutObjectLet the server save cleaned image files in the bucket
s3:GetObjectLet the server create temporary links that display private images

For this integration’s current upload and display flow, the server needs access to put and read objects under the image paths above. It does not need bucket-wide listing or delete permissions for those operations. Keep S3 Block Public Access on, and do not add a public bucket policy or public file ACL. The server does not send files directly from the browser, so S3 browser CORS settings are not needed.

The credential settings are AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY, with AWS_SESSION_TOKEN only for temporary credentials. AWS encrypts bucket data at rest by default. If you select a separate AWS KMS encryption key, the server identity also needs permission to use that key. Check the bucket’s actual region before setting AWS_S3_REGION_NAME.
