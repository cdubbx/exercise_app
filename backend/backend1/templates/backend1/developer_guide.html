Architecture at a glance

The iPhone and Android app sends requests to the Exercise Plus server. The server checks who is signed in, saves workout information, and safely talks to services such as OpenAI, Spotify, and AWS. An API is the set of requests the app and server use to do that. Docker lets you run a local copy of the server while you develop, without changing the live app.

flowchart LR Mobile[Phone app] -->|Secure internet request| API[Exercise Plus server] API <--> DB[(PostgreSQL hosted / SQLite local)] API <--> Redis[(Redis)] API --> OpenAI[OpenAI Responses API] API <-->|OAuth and player requests| Spotify[Spotify] API -->|Private images and timed links| S3[(AWS S3)]

The API reference lists the server requests and phone-app methods. A method is a named task, such as searching exercises or saving a workout. Each entry shows the values it needs, the type of each value, and what it gives back.

Develop with Docker

Install Docker Desktop or Docker Engine with Compose. Start the backend from exercise-backend/backend:

cd exercise-backend/backend
cp .env.example .env
docker compose up --build

The API listens at http://localhost:8000. Compose starts Django and Redis, runs migrations, and keeps SQLite and local media in named volumes. Load the catalog once:

docker compose exec backend python manage.py loaddata fixed_exercises.json

Common commands from the backend directory:

docker compose up -d
docker compose logs -f backend
docker compose exec backend python manage.py test backend1
docker compose exec backend python manage.py makemigrations --check --dry-run
docker compose exec backend python manage.py shell
docker compose down
# Destructive local reset: also deletes SQLite and uploaded media volumes
docker compose down -v

Run the app in another terminal:

cd exercisefrontend
cp .env.example .env
npm ci
npm start

Image uploads with S3

The authenticated app uploads multipart data to POST /api/uploads/. Django limits images to 5 MB and 16 megapixels, accepts JPEG/PNG/WebP, re-encodes pixels to remove embedded metadata, then stores a private object under the user's profile or exercise prefix. Records retain canonical object addresses; API responses issue presigned read URLs that expire after one hour.

sequenceDiagram actor User participant App as React Native participant API as Django API participant S3 as Private S3 bucket User->>App: Choose an image App->>API: POST uploads with JWT and multipart image API->>API: Validate, resize, re-encode, strip metadata API->>S3: PutObject under per-user prefix S3-->>API: Object stored API-->>App: Canonical object URL App->>API: Save profile or exercise record API->>API: Confirm uploaded object belongs to user App->>API: Load profile or exercise API->>S3: Create one-hour presigned GET URL API-->>App: Data with temporary image link

Account deletion removes object versions and delete markers under both prefixes before deleting the account. The server identity needs version-list and version-delete permissions in addition to upload/read access. Treat signed links as temporary bearer links.

Spotify connection and player

Spotify connection has two parts: you approve access once, then the app asks our server to check or control playback. The server makes Spotify requests for the signed-in account. Spotify credentials stay on the server; the app never receives them. The app sends playback controls and displays track information, but it does not carry or play the audio itself.

What happens when you connect

  1. You tap Connect Spotify in the app. The app sends a signed-in request to POST /api/spotify/connect/.
  2. The server creates two short-lived values for this attempt: a random state value and a private verifier. It saves a one-way fingerprint of the state (a hash) and an encrypted copy of the verifier, tied to your Exercise Plus account. They expire after five minutes. State lets the server check that the person returning from Spotify is finishing the same connection that was just started.
  3. The server creates a Spotify authorization link and sends it to the app. It includes a PKCE challenge (“P-K-C-E”): a scrambled version of the private verifier. Spotify receives the challenge, while the server keeps the original verifier. This proves that the callback belongs to the connection request without putting the private verifier in the link.
  4. The app opens Spotify’s sign-in page. Spotify asks you to approve two permissions: reading playback status and controlling playback. These are called scopes—the specific access you are granting.
  5. After approval, Spotify sends the browser back to /api/spotify/callback/ with a short-lived authorization code and the state value. The server checks that the state matches an unexpired connection for your account, then consumes it so it cannot be reused.
  6. The server sends Spotify the authorization code and the private verifier. Spotify returns an access token, which allows requests for a limited time, and a refresh token, which lets the server obtain a new access token later. The server encrypts both before saving them against your account.
  7. The browser shows whether the connection succeeded and provides a link back to the app. The app refreshes its connection status.

Why keep the encryption key stable? SPOTIFY_TOKEN_ENCRYPTION_KEY is the server-only key used to lock and unlock the saved Spotify tokens. Keep it in Heroku’s protected configuration and back it up securely. If you replace it, the server can no longer unlock existing tokens; users will need to connect Spotify again.

What happens when you use the player

The app sends GET /api/spotify/player/ to read the current player, or sends POST /api/spotify/player/ with an action of play, pause, next, or previous. The request includes the Exercise Plus sign-in token; that token proves who is making the request and is separate from the Spotify credentials.

The server unlocks your Spotify access token and asks Spotify for the playback information or control. If the access token is about to expire, the server refreshes it first. If Spotify rejects a request because the token expired, the server refreshes once and retries. Spotify’s reply is reduced to information the app needs: whether music is playing, the track and artists, its artwork and Spotify link, whether a playback device is active, and any controls Spotify has disabled.

Playback controls require Spotify Premium and an account that Spotify allows to use this app. Spotify also needs an active device for the account; if it reports no device, open Spotify and start or resume playback on that account first. Exercise Plus does not stream music, expose Spotify tokens, or send your Spotify credentials to the phone app.

Server settings this feature needs

  • SPOTIFY_ENABLED=true
  • SPOTIFY_CLIENT_ID and SPOTIFY_CLIENT_SECRET from the Spotify developer app. These identify Exercise Plus to Spotify; keep the secret on the server.
  • SPOTIFY_REDIRECT_URI set to the exact HTTPS address https://<your-app-host>/api/spotify/callback/, also entered in the Spotify developer app.
  • A valid, stable SPOTIFY_TOKEN_ENCRYPTION_KEY used only by the server.

Exercise Bot and calendar proposals

The user explicitly allows chat sharing in the app. Django sends the current question and recent conversation to the OpenAI Responses API with store=false and a stable, user-scoped prompt cache key. The bot can propose a calendar workout, but it cannot save one by itself: every exercise must match the catalog, then the user reviews and taps Add to calendar.

sequenceDiagram actor User participant App as React Native app participant API as Django API participant OpenAI as OpenAI Responses API participant DB as Workout database User->>App: Allow sharing and ask a question App->>API: POST gpt-chat with JWT and recent messages API->>API: Validate and apply per-user throttle API->>OpenAI: Instructions, conversation, cache key; store=false OpenAI-->>API: Reply and optional calendar proposal API->>DB: Resolve proposed exercises against catalog API-->>App: Reply and catalog-backed proposal User->>App: Review and confirm Add to calendar App->>API: POST plannedWorkouts with selected day/time/exercises API->>DB: Validate and save plan atomically API-->>App: Saved calendar workout

The bot endpoint is limited to 20 requests per minute by its configured throttle scope. Configure OPENAI_API_KEY on the backend. OPENAI_MODEL is optional and defaults to gpt-4.1-mini.

Calendar planning and edits

Saved exercises and planned calendar entries are separate records. Plans are scoped to the authenticated account and can share a weekday across Morning, Afternoon, Evening, and Anytime slots. The API accepts one plan or a batch of up to eight in a transaction. Editing updates the day, time, sets, or reps.

Heroku environment variables

Examples target the configured Heroku app exerciseplus. Sign in to the CLI. Replace placeholders locally; never commit or share secret values. Add-ons normally populate DATABASE_URL and REDIS_URL.

heroku config -a exerciseplus
heroku config:get DJANGO_DEBUG -a exerciseplus
heroku config:set DJANGO_DEBUG=false -a exerciseplus
heroku config:set DJANGO_ALLOWED_HOSTS='<your-app-host>' -a exerciseplus
heroku config:set AWS_STORAGE_BUCKET_NAME='<verified-bucket-name>' AWS_S3_REGION_NAME='<bucket-region>' -a exerciseplus
heroku config:set OPENAI_API_KEY='<your-api-key>' OPENAI_MODEL='gpt-4.1-mini' -a exerciseplus
heroku config:set SPOTIFY_ENABLED=true SPOTIFY_CLIENT_ID='<client-id>' SPOTIFY_CLIENT_SECRET='<client-secret>' -a exerciseplus
heroku config:set SPOTIFY_REDIRECT_URI='https://<your-app-host>/api/spotify/callback/' -a exerciseplus
heroku config:set SPOTIFY_TOKEN_ENCRYPTION_KEY='<stable-fernet-key>' -a exerciseplus
heroku config:unset OPENAI_API_KEY -a exerciseplus
heroku logs --tail -a exerciseplus

Heroku config output includes credentials; do not paste it into tickets or chat. Prefer the protected config UI or a safe local input method for secrets. Rotating Spotify's encryption key makes existing tokens unreadable, so users must reconnect. Rotate Django's secret key deliberately because it may invalidate signed sessions or tokens. These instructions do not deploy code or alter hosted settings.

Publish a backend update to production

First finish your changes, run the tests, and commit the work you want to release. From the main project folder, use:

git status
# Run tests before publishing
cd exercise-backend/backend
docker compose exec backend python manage.py test backend1
cd ../..
# Publish only the backend folder to Heroku
git subtree push --prefix=exercise-backend heroku master
# Check the release and watch the server logs
heroku releases -a exerciseplus
heroku logs --tail -a exerciseplus

This sends the server code to Heroku. It does not publish a new iPhone or Android app; those builds are released separately. After Heroku reports success, open the website and check the page or feature you changed.

If Git refuses the push: stop and do not force it. This project moved the backend into a larger folder, so the development branch may be missing newer changes already running in production. Those need to be brought into the release branch first. A forced push could replace newer server code with an older version.

AWS S3 setup and access

Create or select the intended private bucket and region, then configure AWS_STORAGE_BUCKET_NAME and AWS_S3_REGION_NAME on the backend. boto3 uses the standard AWS credential provider chain. Prefer an attached role when available; for Heroku, use a dedicated IAM identity with credentials in protected server configuration. Never use an administrator identity or put credentials in the mobile app.

Limit the identity to these key prefixes:

profile-images/<user-id>/<random-uuid>.(jpg|png|webp)
exercises-images/<user-id>/<random-uuid>.(jpg|png|webp)
S3 actionPurpose
s3:PutObjectStore validated uploads
s3:GetObjectSign temporary image-read links
s3:ListBucketVersionsFind object versions and delete markers for account deletion; constrain prefixes where supported
s3:DeleteObject, s3:DeleteObjectVersionRemove owned objects and versions during account deletion

Keep S3 Block Public Access enabled, avoid public bucket policies and ACLs, and use server-side encryption. Browser CORS is unnecessary because uploads pass through Django. For customer-managed KMS encryption, grant only the needed key permissions. Test authenticated upload and signed read, then confirm unsigned object access is denied. AWS credential variables, if needed, are AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, and optional AWS_SESSION_TOKEN. This app reads AWS_S3_REGION_NAME; verify the real bucket region instead of assuming the example default.
